## 2. ローカルデータ所有モデル(決定: アカウント別SQLiteファイル)

- ゲスト: `tsumi-note.db`(現行ファイルをそのまま使用。**移行不要・既存データに一切触れない**)。画像は現行の `note-images/`。
- アカウント(PR 3 の実装): `tsumi-note-acct-<hex(userId)>.db`、画像は `note-images-acct-<hex(userId)>/`(いずれも `documentDirectory` 直下)。
  `hex` はuserIdの各文字コードの16進表記で、メール・表示名は使わない。iOSは大文字小文字を区別しないため、大文字小文字違いのIDが衝突しないようにしている。userIdは `^[A-Za-z0-9_-]{1,128}$` のみ受け付け、それ以外はゲスト扱い(`src/db/ownership.ts`)。
  (当初案の `accounts/<accountKey>/…` + `sha256(userId)` 方式は採用しない。)
- ログアウトしても各DBは削除しない(再ログインで高速復帰)。別アカウントは別ファイルのため **物理的に閲覧不可**。
- アカウント切替時: ①同期ワーカー停止 ②DBハンドルclose ③画面のキャッシュ(クエリ・状態)破棄 ④画像参照ルート切替 ⑤新DBを開いて同期再開。切替処理は単一のAccountContextに集約し、旧アカウントのハンドルが画面に残らないようにする。
- 案B(全テーブルに `ownerId`)は、クエリの条件漏れが漏洩になり既存機能の書き換えが大きいため不採用。

### 端末内データ保護

DBファイル分離だけでは端末内のアクセス防止にならないため、以下を併用する(PR 3 で実装)。

- 保存先はアプリのサンドボックス内(`documentDirectory`)。iOSのData Protection(既定: 初回ロック解除後まで暗号化)に従う。ファイルには明示的に `NSFileProtectionComplete` 相当を指定できる範囲で指定する。
- 認証トークンは `expo-secure-store`(Keychain)に保存し、アクセシビリティは `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`(iCloudキーチェーンに同期しない)。DBや AsyncStorage にトークンを置かない。
- ログアウト時はトークン削除・メモリ上のキャッシュ破棄を必須とする。
- 共用端末向けに「この端末からアカウントデータを削除」を用意する(ゲストDBは無変更)。
- v1ではSQLCipher等によるDB全体暗号化は行わない(Expo managed構成との相性・複雑さのため)。**懸念事項**として記録し、必要なら別途判断する。

## 3. ゲストデータの引き継ぎ(PR 3)

1. 新規・既存アカウントを問わず、ログイン後に端末へゲストデータがあり、そのアカウントで未決定の場合のみ確認シートを表示する。
2. 引き継ぎ = **ゲストDBの内容をアカウントDBへコピー**(ゲストDB・ゲスト画像は削除・変更しない)。D1へのアップロードはPR 4。
   - 「引き継ぐ」: コピーを実行(IDは維持、同一IDは `ON CONFLICT DO NOTHING` で冪等、既存データは上書きしない)。
   - 「引き継がない」: コピーせず、ゲストDBは **残す**(ログアウト後に再びゲストとして使える)。以後たずねない。
   - 「あとで」: 何も保存しない。次回ログイン時・起動時に再び確認する。
3. 失敗・中断時は再試行可能(再実行しても重複しない)。画像コピーの順序と失敗時の扱いは「PR 3 実装メモ」を参照。
4. **引き継ぎ決定の保存先は、決定の対象となる「アカウントDB」の `sync_metadata`**(キー `guest_import:<ゲストDB名>`、値 `imported` / `declined`)。
   アカウントごとに別DBのため、アカウントAの決定はアカウントBに影響しない(Aで「引き継がない」でも、Bでは未決定として確認される)。
   ゲストDBには何も書き込まない(ゲストDBは無変更の原則)。ゲストデータは自動削除しない。

## 4. 同期プロトコル(PR 4)

### 4.1 サーバー側(D1)

- 全同期テーブルに `user_id` を持たせ、**すべてのクエリで認証済みセッションの `user_id` を条件にする**(クライアント送信のuserIdは使わない)。
- 各行に `server_seq`(ユーザー単位で単調増加)を採番し、これを **同期カーソル** とする。端末時計には依存しない。
- 画像は `note_images`(id, user_id, sha256, size, content_type, deleted_at)。実体はR2(キー `users/<userId>/<sha256>`)。

### 4.2 エンドポイント(Hono)

- `POST /v1/sync/push`: 変更バッチ(最大N件)。`opId` で冪等。バッチ単位でトランザクション。
- `GET /v1/sync/pull?cursor=<server_seq>&limit=N`: `server_seq > cursor` の差分をページング。
- 画像: `PUT /v1/images/:sha256`(存在すればスキップ)、`GET /v1/images/:sha256`(Worker経由で認可して配信)。
- すべて `/v1/*` の認証ミドルウェア(検証済みセッション必須・メール確認済み必須)の配下に置く(PR 1 で実装済み)。

### 4.3 変更検知(決定: Outbox)

- クライアントに `sync_outbox`(opId UUID, entity, entityId, operation(upsert/delete), payload, createdAt, sentAt)を追加。
- **ローカルデータの変更とoutbox登録は同一トランザクション**。登録漏れ防止のためリポジトリ層の書き込み関数に集約する。
- 送信 → サーバーが `opId` を記録(同じopIdは再処理せず前回結果を返す=冪等) → 成功後に `sentAt` を更新。失敗時は未送信のまま再送。
- 削除もoutboxの `delete`(tombstone)として同期する。
- `sync_metadata` に cursor / lastSyncedAt / deviceId を保存。端末の `updatedAt` は順序判定に使わない。
- トリガー: 起動・フォアグラウンド復帰・ローカル変更後(デバウンス)・手動。UIをブロックしない。失敗時は指数バックオフ。
- ログアウト/アカウント切替時は同期を停止し、DBハンドルを切り替える。

### 4.4 競合解決(決定: 競合コピー)

原則: **ユーザーが入力した内容と学習履歴を失わない**。順序は常に「サーバーが受信した順(server_seq)」で決める。

| 対象 | 方式 |
|---|---|
| `study_sessions` `answer_history` `review_history`(Append-only) | IDで重複排除して和集合。更新・削除しない。同時追加でも両方残る |
| `fsrs_states` | **(PR 4 で変更)** 履歴からの再計算は行わず、「最後に復習した状態を採用」する可換な統合(後述 §10)。履歴は両方残る |
| `notes` | 競合コピー対象。本文・タイトルが競合した場合、server_seqで後の変更を本体に採用し、**上書きされる側の内容を新しいノート(競合コピー)として保存** |
| `questions` | 競合コピー対象。上書きされる側を別の問題として保存。競合コピーは新規問題(新ID・FSRS状態は新規)で、元問題の履歴は元IDに残る |
| `folders` | 行単位LWW(server_seq)。名前の競合はコピーを作らない(内容損失が小さいため)。 |
| `goals` / 行動プラン / `settings` | 行単位LWW(server_seq)。コピーは作らない |
| 削除 vs 編集 | 削除(tombstone)を維持し、削除を上書きする復活はさせない。**ただし編集側がノート・問題の場合は編集内容を競合コピーとして保存**し、内容を失わない |
| 削除済みIDの再出現 | サーバーが拒否(tombstoneが勝つ)。古い端末からのupsertで復活しない |
| フォルダー削除 vs ノート移動 | 参照先が削除済みのノート・問題はフォルダー未所属(ルート)に移す。参照整合性を維持 |

競合コピーの扱い:

- **(PR 4 で変更)** `conflictOfId` カラムは追加せず、競合コピーは **タイトル(ノート)/問題文(問題)の先頭に「【競合コピー】」を付ける** ことで識別する(既存スキーマ・既存画面を変えずにユーザーに見える。カラム追加とバッジ表示は PR 6 で検討)。
- UI(以下は PR 6 で検討): 一覧・詳細に「競合コピー」バッジを表示し、元との比較・コピーの統合(内容を元へ反映)・削除ができる(PR 4 〜 6 で実装。Figmaは未デザインのため既存コンポーネントで仮実装し、その旨をPRに記載)。
- 競合コピーも通常の行として同期される(別端末にも同じコピーが現れ、重複作成しない: コピーIDはサーバーが決定的に生成する)。

## 5. ノート画像(決定: マッピングテーブル方式 / PR 5)

- **既存の画像ファイル名とMarkdown本文の `note-image://<fileName>` は変更しない。**既存ノートを壊す移行は行わない。
- ローカルに `note_image_assets`(fileName 主キー, sha256, size, remoteKey, uploadState, downloadState, updatedAt)を追加し、ローカルファイル名 ↔ sha256 ↔ R2オブジェクトの対応を管理する。
- sha256が同一の画像は、R2へは1オブジェクトのみアップロード(`PUT` 前に存在確認)。複数のfileNameが同じsha256を指してよい。
- 状態: `pending_upload / uploaded / pending_download / downloaded / failed`。アップロード失敗でもローカル画像は保持し、再試行する。
- 他端末: Markdown内の `note-image://<fileName>` が未取得なら、マッピングからR2を取得してローカルに同名保存して表示する。
- 未使用画像の削除: どのノート(削除済み含む)からも参照されず、猶予期間(例: 30日)を過ぎたもののみ。参照状態を毎回確認する。
- 画像データはD1に入れない。R2キーは `users/<userId>/<sha256>`、ユーザー単位で認可する。

### 6.2 メール+パスワード(PR 1 実装)

- 確認メール必須(`requireEmailVerification`)。未確認ではセッションを発行せず403。**確認後も自動サインインしない**(Expoプラグインが `tsumi-note://` への遷移URLにセッションCookieを `cookie` クエリとして付与し、同じschemeを登録した別アプリへ漏れるため)。確認リンクはHTTPSのAPIで処理し、セッションなしで `tsumi-note://verified` を開く。ユーザーはアプリで改めてログインする。`app.ts` の `stripCredentialsFromRedirect` が確認・再設定レスポンスから Set-Cookie と認証情報クエリを多層防御として除去する。
- 確認・再設定トークンの有効期限は1時間。再設定後は全セッションを失効。再設定トークンは使い捨て。
- パスワードポリシー: 10〜128文字、英字+数字、メールのローカル部を含まない。登録・再設定・変更のすべてに適用(`api/src/password-policy.ts`)。
- 列挙対策: 未登録メールへの再設定要求・ログイン失敗・登録済みメールでの再登録は、外形上同じ応答。登録済みメールには本人にだけ通知メールを送る。送信は `waitUntil` で応答と非同期に行う。
- レート制限(IP単位・D1保存、`cf-connecting-ip` のみ信頼): ログイン 5回/分、新規登録 5回/5分、確認メール再送・再設定メール 1回/分、再設定・変更 5回/分、既定 60回/分。
- メール送信失敗はログ(宛先・本文・リンクを含まない)に残す。本番でAPIキー未設定の場合は送信が失敗する(黙って成功扱いにしない)。
- セッション: 有効30日(1日ごとに更新)。`BETTER_AUTH_SECRET` が未設定/32文字未満ならWorkerは500を返し起動しない。
- `/v1/*` は検証済みセッション+メール確認済みを必須とするミドルウェア。ユーザーIDは常にセッション由来。

### 6.3 アカウント連携(決定)

- v1では連携機能を実装しない。`accountLinking` は無効で、**メールが同じでも別プロバイダーのアカウントを自動統合しない**。
- 同じプロバイダーの同じアカウント(`providerId` + `accountId`)での再ログインは既存ユーザーとして扱う。
- データモデルは `user` 1 : N `account`(providerId, accountId, password…)。将来、ログイン済み+再認証を伴うフローで `account` 行を追加すれば連携できる。

## 7. ログアウト / アカウント削除(PR 6)

- ログアウト: セッション破棄・同期停止・DBをゲストへ切替。**アカウントDBは端末に残す**。未同期変更がある場合は警告し「同期してからログアウト」を提示。
- アカウント削除: 再認証 → サーバー: ①全セッション失効 ②D1データ削除 ③R2の `users/<userId>/` 削除 ④Better Authユーザー削除。各段階は冪等でリトライ可能(`deletion_jobs`で進捗管理)。
- 他端末: 次回同期で401/`account_deleted`を受け、同期停止・アカウントDBを削除してゲストへ戻る(ゲストDBは無変更)。

## PR 3 実装メモ: アカウント別DBとゲスト引き継ぎ

- **DB選択**: `AuthProvider` の内側の `DatabaseProvider` が認証状態から所有者を決める(`src/db/resolve-owner.ts`)。signedIn=アカウントDB、signedOut=ゲストDB、loading=前回確定した所有者(Keychainの不透明なID。無ければゲスト)。ログアウトでヒントを削除。サブツリーは DB名を `key` にして再マウントするため、前の所有者の画面・フック・状態は残らない。旧接続は新DBが有効になった後に閉じる。認証失敗時は状態が変わらないためDBも変わらない。
- **引き継ぎ**(`src/db/guest-transfer.ts`, `run-guest-import.ts`): ユーザーが「引き継ぐ」を選んだ場合のみ実行。ゲストDBは別接続で読み取り、アカウントDBへ **1トランザクション** で `INSERT ... ON CONFLICT DO NOTHING` し、同じトランザクションで `imported` を記録する。IDと参照関係を維持し、既存の行・設定は上書きしない。単一アクティブ目標(v1)を守るため、アカウントに既に目標がある場合はゲストの目標をコピーしない。再実行しても重複しない。ゲストDB・ゲスト画像は変更・削除しない。
- **確認**: §3 のとおり。決定は **アカウントDBの** `sync_metadata`(`guest_import:<ゲストDB名>`)に保存し、「あとで」は保存しない。
- **画像と順序**(`src/features/notes/copy-images.ts`, `note-image-store.ts`): ファイルコピーとDBトランザクションは原子的にできないため、次の順序とする。
  1. すべての画像コピーを `await` で完了させる(`File.copy()` / `move()` は `Promise<void>`)。
  2. **画像は不変ファイル**(ファイル名は新規ID `<id>.<ext>`。同名=同内容)。そのため既存ファイルの置換・バックアップは行わず、**欠けているファイルを追加するだけ**にした(旧案の `.backup` 方式は廃止)。内容の一致はサイズではなく **SHA-256**(`expo-crypto` + `File.bytes()`)で判定する。
  3. 各ファイルは `<name>.partial` へコピー → SHA-256がコピー元と一致するか検証 → 本来の名前へ `move`(`overwrite` なし。expo は先に移動先を削除するため使わない)→ 移動後に再度ハッシュ検証。
  4. 1つでも失敗(例外・ハッシュ不一致・競合)したらDBは一切触らず、`imported` も記録しない。DB行のコピーと `imported` の記録は、全画像成功後に1トランザクションで行う。
  5. 再試行・中断回復(`.partial` は最終ファイルが無いときにのみ作られる):
     - 最終ファイルのハッシュ=コピー元 → 完了。`.partial` を破棄。
     - 最終ファイル無し + `.partial` のハッシュ=コピー元 → 検証済みなので `move` のみ。ハッシュ不一致の `.partial` は破棄して再コピー。
     - 最終ファイルが不一致 + ハッシュ一致の `.partial` があり、最終ファイルが `.partial` の**先頭部分と一致** → 中断した `move`(Androidはネイティブ移動に失敗するとコピー後削除へフォールバックするため、途中までのコピーが最終名に残りうる)。証明できた不完全コピーのみ削除して `move` し直す。
     - それ以外の不一致(サイズ一致・内容不一致を含む) → 自分のものと証明できないため**削除も上書きもせず**エラー(`ImageConflictError`)。`imported` は記録しない。
  6. 同時実行は直列化する。孤立画像の掃除は `.partial` を対象にしない。ゲスト側の画像は読み取りのみ。
  - DBコミットが失敗した場合は画像だけがコピー済みだが、どのノートからも参照されない孤立ファイルで、再試行時に再利用される。DBに画像参照だけが残り実ファイルが無い状態にはならない(ゲスト側で元々欠落している画像は除く)。
  - 整合性はファイルサイズではなく、コピー元・`.partial`・コピー先のSHA-256の一致で判断する(上記 3・5)。サイズ一致だけでは完了とみなさない。PR 5 の `sha256` マッピングは、アップロード側で同じ内容検証を使う想定。
- **PR 4 への準備**: 既存の `createdAt/updatedAt/deletedAt`、追記型履歴は変更していない。同期・D1への送信は未実装。

## 10. PR 4 確定仕様: 差分同期

実装: サーバー `api/src/sync/`、クライアント `src/sync/`、ローカルmigration `drizzle/0004_sync_outbox.sql`、D1 migration `api/migrations/0001_sync.sql`。§4 との差分は本節が優先する。

### 10.1 同期対象

| エンティティ | 種別 | 備考 |
|---|---|---|
| folders / notes / questions / goals | mutable(tombstone) | notes・questions は競合コピーあり |
| study_sessions / answer_history / review_history | append(IDで重複排除) | 更新・削除しない |
| fsrs_states | fsrs(最後に復習した状態を採用) | 問題ID単位 |
| settings | setting(到着順の後勝ち) | **許可リスト**のみ: `review.*` / `timer.focusMinutes` / `timer.breakMinutes` / `timer.rounds` / `appearance.darkMode`。通知設定・タイマー実行状態・選択中フォルダーは端末固有なので同期しない |

画像本体は PR 5。`note-image://<fileName>` の参照はノート本文のまま同期される。他端末で画像ファイルが未取得の間は画像が表示されないだけで、本文・参照は壊れない。取得状態の管理と表示の補完は PR 5。

### 10.2 クライアント

- **変更検知**: DBトリガー(`sync_capture_*`)が、変更と同じ文(=同一トランザクション)で `sync_outbox` に登録する。リポジトリ層は変更していない。
  - `sync_metadata.sync.capture = '1'` のDBでのみ有効。**ゲストDBでは常に無効**で、既存データにも触れない。
  - 同期エンジンがサーバーの内容を反映する間は `0` にし、反映した変更が再送されないようにする(トランザクション内なので、失敗すれば自動で元に戻る)。
  - outbox は参照のみ(`entity`, `entity_id`)。送信時に現在の行を読み、同じレコードの複数回の編集は1件にまとめる。
- **有効化**(`enableSync`、1トランザクション): DBの持ち主(`sync.owner`)が別アカウントなら拒否。初回のみ既存の全レコードを outbox に登録する(ゲストから引き継いだデータ、migration前のデータを含む)。
- **送信**: 親 → 子の順(フォルダー → ノート/問題 → 履歴)に最大50件ずつ。`opId = <deviceId>-<outbox seq>`。**サーバーが反映を返したレコードだけ**、送信時点までの outbox を削除する。それ以降の編集は残る。失敗時は何も消えず、次回続きから再送する。
- **取得**: `cursor`(サーバーの `server_seq`)以降を100件ずつ。ページの反映とカーソル更新は同一トランザクション。未送信の編集があるレコードは上書きせず、次の送信で競合として解決する。
- **ベース版**: `sync_record_meta` に各レコードの最後に知った `server_seq` を保存し、送信時に `baseSeq` として送る(同時編集の検出に使う。端末時計は使わない)。
- **停止**: `isActive()` が false(ログアウト・アカウント切替・画面破棄)なら通信も反映もしない。応答の `userId` が DB の持ち主と違う場合は何も反映せず停止する。`SyncProvider` は DB と同じ `key` 配下にあり、DB切替で破棄される。
- **実行制御**(`controller.ts`): 同時に1つだけ実行、実行中の要求は終了後に1回に集約。通信失敗は `offline`、サーバー失敗は `error` として 5s → 15s → 60s → 300s で再試行。認証エラーは再ログインまで再試行しない。トリガー: 起動、フォアグラウンド復帰、ネットワーク復帰、ローカル変更(3秒デバウンス・未送信がある場合のみ)、5分周期、手動。
- 反映した変更を画面へ即時に再描画することはしない(編集中の画面を作り直さないため)。次に画面を開いたとき、またはフォーカスが戻ったときに反映される。

### 10.3 サーバー(Workers / Hono / D1)

- `POST /v1/sync/push`(最大100件・本文150万文字まで)、`GET /v1/sync/pull?cursor=&limit=`(最大100件・約100万文字ごとに分割)。どちらも `/v1/*` ミドルウェア(検証済みセッション・メール確認済み)配下。
- テーブル: `sync_records(user_id, entity, id, data JSON, deleted_at, server_seq)`、`sync_counters`(ユーザーごとの採番)、`sync_ops(user_id, op_id, server_seq)`。すべて `user_id = <セッションのユーザー>` で絞る。リクエストにユーザーIDを受け付けるフィールドは無く、未知のフィールドは400。
- 入力検証: エンティティごとに全列を厳密に検証(未知のキー・欠落・型・長さ・列挙値)。ID は `[A-Za-z0-9._~:-]{1,128}`。SQL は全てバインドパラメータ。
- **原子性と順序**: 1リクエストの書き込みは1回の `batch`(D1ではトランザクション)。`server_seq` はユーザーごとのカウンタで書き込み順に採番する。各書き込みは「読んだ時点の `server_seq` と一致する場合のみ」反映し(楽観ロック)、同時に別リクエストが更新していた場合は `retry` を返して反映しない。クライアントは未送信のまま再送する。
- **冪等性**: 反映された操作の `opId` を `sync_ops` に記録し、同じ `opId` の再送は前回の結果を返す(応答が失われた再送が、他端末の新しい更新を巻き戻さない)。履歴は同じIDなら何度送っても1件。
- ログには学習データ・トークンを出さない。

### 10.4 競合解決(確定)

順序は常に **サーバーの受信順(`server_seq`)**。端末の `updated_at` は順序判定に使わない。

| 状況 | 結果 |
|---|---|
| サーバーに無い | 採用 |
| 内容が同一 | 何もしない |
| `baseSeq` = サーバーの最新(最新版を見た上での編集) | 採用 |
| 同時編集(notes / questions) | 後着を本体に採用し、**先着の内容を競合コピー**として保存 |
| 同時編集(folders / goals) | 後着を採用(コピーなし。内容損失が小さい / 目標は1件のみの制約のため) |
| 削除 vs 編集 | 削除を採用し、他端末の編集内容(notes / questions)を競合コピーとして保存 |
| 削除済みを古い端末が編集して再送 | **復活させない**(`superseded`)。編集内容(notes / questions)は競合コピーとして保存。クライアントはサーバーの削除を採用 |
| append(履歴) | 既存IDは再書き込みしない。両端末の履歴は和集合 |
| fsrs_states | (最後の復習時刻, 復習回数, 更新時刻) の大きい方を採用。順序によらず結果が同じ |
| settings | 到着順の後勝ち |

- 競合コピーのIDは `<元ID先頭80文字>~c<内容のハッシュ>`。同じ内容の再送で増えず、別の内容は別コピーになる。コピーは通常の行として他端末にも同期される。
- 競合コピーはタイトル / 問題文の先頭に「【競合コピー】」が付く。ノートのコピーは `pinned = 0`。問題のコピーは新規カード(FSRS状態なし)で、元の問題の履歴は元IDに残る。
- 競合が検出された件数は同期結果(`conflicts`)として返り、同期状態の表示に出る。

#### 送信中のローカル編集の保護

- 送信時に `opId = <deviceId>-<outbox seq>` の `seq`(送信済みの範囲)を記録する。応答の反映時、**同一トランザクション内**で「その `seq` より後の outbox があるか」を確認する。
- 後続の編集・削除がある場合、`superseded` の `current` でローカルの行を**上書きしない**。ベース版(`baseSeq`)も進めず、送信済みの範囲だけを outbox から外す(後続分は残る)。次の送信は同時編集として扱われ、サーバー側が削除済みでも後続の内容が競合コピーとして保全される(送信済みの内容は、前回の応答の時点でサーバー側に競合コピーとして保存済み)。
- 後続の編集が無い場合は、従来どおりサーバーの内容(削除を含む)を採用する。
- 通信失敗・応答の消失後も outbox が残るため、再試行で同じ処理が行われる(`opId` により二重適用しない)。

#### APIの互換性方針(未対応 entity)

- サーバーは、クライアントより新しい entity を先に配信しうる(サーバー先行デプロイ)。クライアントは**未対応の entity を含むページを一切反映せず、カーソルも進めずに** `SyncUpdateRequiredError` で停止する(ページの反映とカーソル更新は同一トランザクションのため、取りこぼしは起きない)。
- 停止したページより前のページは反映済み。ローカルのデータと未送信の変更は失われない。送信(push)は取得の前に完了している。
- コントローラーは `update-required` 状態にし、**タイマーによる自動再試行はしない**(無限リトライの防止)。画面には「アプリを更新すると同期を続けられます」と表示する。次回のトリガー(起動・手動など)では再度取得を試みる。
- アプリ更新後は、保存済みカーソルから同じ変更を再取得して反映する(取得は冪等)。
- 既存 entity の削除・意味の変更は行わない(新しい entity の追加のみ)。列の追加など個別の互換性は、追加するときに別途検討する。

### 10.5 既知の制限・懸念(PR 4 時点)

1. **FSRS状態は履歴からの再計算ではなく「最後の復習を採用」**。履歴には「予定を更新しない復習(`keepSchedule`)」かどうかが記録されておらず、単純に再生すると別の状態になりうるため。2台で同時に復習した場合、新しい方の結果が採用され、もう一方の復習は履歴には残るが、スケジュールには反映されない。
2. goals / folders / settings は同時編集でコピーを作らない(後着が採用され、先着の内容は残らない)。行動プランを両端末で同時に編集すると片方が失われる。
3. 目標は1件のみという制約はリポジトリ層で守っているため、2台で別々に目標を作ると同期後に2件になる。
4. 削除済みフォルダーに属するノート・問題は、DBには残るが画面には表示されない(従来のフォルダー削除と同じ挙動)。
5. `sync_ops` は削除していない(増え続ける)。アカウント削除(PR 6)でユーザーごと削除される。古い操作の整理は未実装。
6. 同期APIのレート制限は未実装(件数・サイズの上限のみ)。
7. D1 の `batch` 内で `changes()` を使う記述(操作IDの記録)と、実際の Workers / D1 環境での動作は未確認(テストはSQLiteで実施)。

## 11. PR 5 確定仕様: ノート画像の同期(R2)

§5 の方針(既存のファイル名・Markdown参照は変更しない、sha256で重複排除、D1に画像本体を入れない)を次のとおり実装した。§5 から変わった点は「ローカルの管理テーブルを `image_transfers` に簡素化」「R2キーを `u/<userId>/<sha256>` に変更」「削除の条件をサーバー側で判定」の3点。

### 11.1 ローカル(SQLite)

- 画像ファイルは従来どおり `note-images/`(アカウントは `note-images-acct-…/`)に保存する。画像はまず端末に保存され、オフラインでも表示できる。
- 転送状態は新テーブル `image_transfers`(file_name, sha256, state, attempts, last_error, updated_at)で**ファイルごとに**管理する。D1の同期カーソル・outbox とは独立しており、同期対象外・引き継ぎ対象外(端末内の記録のみ)。追加のみの migration(`0005`)で、既存データは変更しない。
- `state`: `uploaded`(サーバーのR2保存を確認済み)/ `upload_failed` / `download_pending`(他端末のアップロード待ち)/ `download_failed` / `rejected`(サーバーが形式・サイズ等で拒否。再送しない)。行が無い = 未転送。
- **R2への保存成功の応答を受けるまで `uploaded` にしない。** 失敗・中断・認証切れ・オフラインでもローカルのファイルは変更・削除しない。
- ダウンロードは `<name>.partial` に書いてから移動し、取得したバイト列の sha256 がサーバーの値と一致しなければ保存しない。既存のファイルは上書きしない。

### 11.2 同期の順序

`pushImages`(未アップロードの画像を送る + 不要な画像の削除依頼)→ D1差分同期(PR 4)→ `pullImages`(反映されたノートが参照する未取得の画像を取る)。ノートの参照より先に本体がR2に届くため、通常は他端末でノートを開いた時点で画像が揃う。それでも未到着(アップロード待ち)の間は、本文とMarkdown参照は壊れず、画像だけ表示されない(取得できたら次に画面を開いたときに表示される)。画像の失敗でD1の同期は止めない(再ログインとアカウント切替による停止は伝える)。アップロード対象は、削除されていないノートが参照している端末内の画像のみ。1回の同期で最大20ファイル、残りは次回。

### 11.3 サーバー(Workers / D1 / R2)

- D1 `image_objects`(user_id, file_name, sha256, size, content_type, r2_key, created_at, deleted_at。主キーは (user_id, file_name))。**D1の行は R2 への保存が成功した後にだけ書く**(行がある = 本体がある)。
- API(すべてセッション必須。ユーザーIDは常にセッション由来):
  - `PUT /v1/images/:fileName`(ヘッダー `x-content-sha256` 必須)
  - `GET /v1/images/:fileName`
  - `DELETE /v1/images/:fileName`
- **オブジェクトキーはサーバーが `u/<userId>/<sha256>` で決める。**クライアントが指定できるのはファイル名だけ。バケットは非公開(公開URL・カスタムドメインを設定しない)で、Worker経由でしか読み書きしない。クライアントにR2の資格情報は渡さない。
- アップロード検証: ファイル名規則(`note-images.ts` と同じ)、15MB以下、先頭バイトによる実形式の判定(JPEG/PNG/GIF/WebP/HEIC)、**拡張子・実形式・Content-Type の一致**、sha256の一致。保存する Content-Type はクライアントの申告ではなく判定結果。
- 重複排除: 同一ユーザー・同一sha256のオブジェクトは1つ。2回目以降は本体を送り直さない。同じ画像名で別内容は 409(画像名は不変)。同じ操作の再送は冪等。
- 他ユーザーの画像・存在しない画像・削除済みはすべて同じ 404(存在を推測させない)。他人の画像は削除もできない(自分の行として存在しない)。
- 削除(冪等)は次の場合に 409 で拒否する: ①同期済みの有効なノートがまだ参照している(`in_use`)、②アップロードから24時間以内(`recently_uploaded`。参照するノートの同期が追いつく前に消さない)。削除は行を論理削除し、同じ内容を指す他の行が無いときだけR2の本体を消す。

### 11.4 削除の反映とノート削除時の扱い

- ノートを削除しても、その時点では画像を消さない(ノートは tombstone として残る)。既存の掃除(`sweepNoteImages`)が端末内の画像を消した後、次の同期で「サーバーに保存済み(`uploaded`)なのに端末に無く、どのノートも参照していない」画像についてサーバーへ削除を依頼する。参照中・猶予中ならサーバーが拒否し、行を残して後で再確認する。
- 他端末も、同期で参照が無くなれば同じ掃除で端末内の画像を消し、サーバーへの削除依頼は「既に削除済み(`absent`)」で冪等に終わる。削除済みの画像は他端末から取得できない(404)。
- 未アップロードの画像、または端末にある画像は、この経路では削除されない(端末のファイルを消すのは従来の掃除だけ)。

### 11.5 アカウント分離・ログアウト・引き継ぎ

- 端末内のディレクトリ・DB・`image_transfers` はアカウントごと(PR 3)。ログアウトしてもアカウントの画像は削除しない。同じアカウントで再ログインすれば、端末に残っていればそのまま、無ければ(再インストールなど)ノートの参照から取得して復元する。
- ゲストデータの引き継ぎ(PR 3)は画像ファイルもコピーする。引き継いだ画像は、アカウントDBの同期開始後の最初の同期でアップロードされる(ゲストの画像は削除しない)。
- アカウント削除(PR 6)では、R2の `u/<userId>/` 配下をすべて削除する必要がある。D1の行は `ON DELETE CASCADE` で消えるが、R2は消えない。

### 11.6 既知の制限・懸念(PR 5 時点)

1. 実際の Cloudflare R2 / Workers での動作と、実機(iPhone/iPad)間の画像表示は未確認(テストはメモリ上のR2代替とSQLite)。
2. ダウンロード/アップロードは1ファイルを丸ごとメモリに載せる(上限15MB)。大きな画像の連続転送は端末・Workerのメモリを使う。
3. ダウンロードで反映された画像は、編集中の画面を再描画しないため、次に画面を開くときに表示される。転送状態の画面表示(未アップロード件数など)はPR 6。
4. 削除済みノートの履歴は残るため、ノートを復元する機能を将来追加する場合は、サーバー側で画像が先に削除されないよう猶予を見直すこと。
5. 画像を参照する本文は notes のみ(問題文・解答は画像に未対応)。
6. 画像APIにレート制限は未実装(サイズ上限と認証のみ)。

## 12. PR 6 確定仕様: マイページ・ログアウト・アカウント削除

### 12.1 マイページ
- ゲスト: 「ゲストとして利用中」の説明(記録は端末に保存、全機能が使える、ログイン時に引き継ぎを選べる、ゲストの記録は削除されない)と、ログイン導線。アカウント作成は既存のFigma 15のボタン。
- ログイン中: メールアドレス・ログイン方法(`GET /v1/account` の `providers`)・同期状態バッジ・最終同期日時・今すぐ同期・ログアウト・アカウント削除。
- 同期状態は既存の `SyncProvider`(D1差分 + R2画像)の値をそのまま表示する: 同期済み / 同期中 / 未同期あり / オフライン / 同期エラー / 再ログインが必要 / アプリの更新が必要。最終同期日時は `sync.lastSyncedAt`(同期が成功した時刻だけを記録)。
- 手動同期は既存の `controller.trigger()`。同時実行は1つだけ(既存)で、同期中・準備中・アプリ更新が必要な間はボタンを無効にする。

### 12.2 ログアウト
サインアウト → 認証状態が変わる → `DatabaseProvider` が所有者をゲストへ切り替えて画面ツリーごと再マウント。`SyncProvider` も破棄され、`controller.stop()`・画像通信の中断が走る(進行中の同期は完了後の書き込みも `isActive` で止まる)。アカウントDB・アカウント画像・R2は**削除しない**。再ログインすると同じ `tsumi-note-acct-<id>.db` を開く。未同期の変更があれば確認シートで件数を警告する(データは端末に残り、再ログインで同期が続く)。サーバーに届かない場合でも、クライアントはサーバー呼び出しの前にローカルのセッションを消去する(Better Auth Expo の仕様)。

### 12.3 アカウント削除(サーバー)
`DELETE /v1/account`(本文 `{ confirm: true, password? }`)。対象は常にセッションのユーザーで、他人のIDを指定する入力はない。
1. **本人確認**: パスワードのあるアカウントは現在のパスワード(`ctx.password.verify`)。誤りは403、ユーザー単位で5回/分を超えると429。パスワードのないアカウント(Apple/Google)は、ログイン(セッション作成)から5分以内であること。超えていれば `reauth_required`(403)。
2. `account_deletions` に依頼を記録。**以降このユーザーは `/v1/*` が `401 account_deleted`**(削除の再試行を除く)になる。他端末の同期・画像アップロードはここで止まり、古いデータは再アップロードされない。
3. R2 の `u/<userId>/` 配下を削除。**失敗したら user 行を消さず500**(セッションが残るので同じ要求で再試行できる)。
4. D1: `verification`(再設定トークン)・レート制限行・`user` を1つのbatchで削除。`session / account / sync_* / image_objects` は `ON DELETE CASCADE`。
5. 並行アップロードの取りこぼしをR2から再度掃除し、`completed_at` を記録。ここの失敗は握りつぶさずログし、`completed_at IS NULL` かつ user が存在しない行を **cron(毎日)の `sweepDeletions`** が再実行する。
- 成功(`deleted: true`)は手順4まで終わってから返す。何度呼んでも同じ結果(冪等)。`account_deletions` には不透明なユーザーIDと時刻のみ(個人情報なし)。
- 削除対象はすべて `user_id = セッションのユーザー` で絞る。R2は `u/<そのユーザーID>/` のみ。他アカウントには触れない(テストで確認)。

### 12.4 アカウント削除(端末)
1. サーバーが `deleted: true` を返すまで、端末のデータ・セッションには一切触れない(通信失敗・サーバー失敗時は再試行できる)。
2. 成功後、Keychainに「削除予約」(アカウントIDのみ)を保存し、サインアウトする。
3. 所有者がゲストに切り替わり、アカウントDBが閉じられた後に、そのアカウントのDB(`deleteDatabaseAsync`)と画像ディレクトリを削除して予約を消す。アプリが途中で終了しても次回起動で続きを実行する。使用中のDB・ゲストDB・ゲスト画像・他アカウントは削除しない(名前はアカウントIDから導出したものだけ)。
4. 削除後はゲスト状態に戻る。ゲストのデータは無変更。

#### 12.3.1 削除と画像アップロードの競合対策(レビュー対応)

- 画像PUTは R2 に書く前に `image_uploads`(進行中アップロードの記録)を作る。作成は「`account_deletions` に行が無いこと」を条件にした1文(原子的)で、削除依頼後は作れず 401。複数Workerインスタンス間でも D1 の直列性で成立する。
- 削除は依頼記録 → R2削除 → **有効なアップロード記録が残っていれば user 行を消さず 500(再試行)** → user 削除 → R2再掃除 → `completed_at` 確定。記録は `UPLOAD_LEASE_MS`(10分)で失効し、異常終了したアップロードが削除を妨げ続けない。
- アップロード側は書き込み後(例外時も)に削除依頼を再確認し、依頼済みなら自分で R2 オブジェクトと行を取り消して 401 を返す。取り消しに失敗した場合は記録を残し、`sweepDeletions` が失効後に再掃除してから `completed_at` を確定する(有効な記録がある間は完了にしない)。
- `completed_at` は「有効なアップロードが無い状態で R2 の最終掃除が成功した後」にだけ確定する。

#### 12.3.2 削除の再試行

- 削除依頼済みのアカウントでも `GET /v1/account`(`deletionPending: true`)と `DELETE /v1/account` だけは通す。同期・画像・その他の `/v1/*` は 401 のまま。再試行でもパスワード/直近ログインの本人確認とレート制限を行う。
- アプリはログイン方法を取得できなくても削除ボタンを無効にしない(入力されたパスワードを送り、判断はサーバー)。`deletionPending` のときは「削除を再試行」と案内する。

### 12.5 他端末の扱い・採用しなかった案
- 他端末は次回の同期で `401`(`account_deleted` または セッション失効)を受け、同期状態が「再ログインが必要」になる。アカウントDBは**自動では削除せず**、ユーザーがログアウトしたあとも端末に残る(データ消失防止を優先)。削除済みアカウントでは再ログインできないため、端末内のそのアカウントのデータは現状は不可視のまま残る(§12.6)。
- `deletion_jobs` テーブルによる段階管理は採用せず、各段階が冪等な単一エンドポイントの再送で再開する方式にした。

### 12.6 懸念事項
1. 他端末に残る削除済みアカウントのローカルDBは、自動では消えない(ストレージを消費する。将来、起動時に `account_deleted` を受けたら削除予約を作る案がある)。
2. 削除成功の応答が失われた場合、再試行は401になり「ログインの有効期限切れ」と表示される(すでにサーバー側は削除済み)。端末のデータはログアウト後も残る。
3. Apple/Google のみのアカウントは「5分以内のログイン」で本人確認とするため、期限切れの場合は一度ログアウトして再ログインが必要。
4. R2削除は `list` + 一括 `delete`。大量の画像があるとWorkerの1回の実行時間・サブリクエスト上限に達する可能性があり、その場合は500を返して再試行で続きから削除される。
5. Figma 16・17・18 は取得できていないため、マイページ(ログイン中)と確認シートは未デザインの仮実装。

#### 12.3.3 失効したアップロードの遅れた書き込みの回収

- lease(10分)の失効は「書き込みが止まった」ことを意味しない。失効後に再開したアップロードも、書き込み後に必ず削除依頼(`account_deletions`、削除後も残る)を再確認し、依頼済みなら自分で取り消して 401 を返す。確認自体に失敗した場合は握りつぶさず 500 にする。
- 取り消す前に `r2_cleanup_tasks`(migration `0005`)へ掃除タスクを記録する。R2 の削除に失敗してもタスクは残り、削除が完了済みで `image_uploads` が消えていても定期掃除 `sweepCleanupTasks` が冪等に再試行する(失敗はログに出す)。
- 掃除は削除依頼のあるユーザーの `u/<userId>/` 配下のキーに限るため、他アカウントの画像には触れない。

#### 12.3.5 掃除タスクの保持期間(リース失効 ≠ PUT完了)

- `sweepCleanupTasks` は、R2 のキーを削除してもタスクを**すぐには消さない**。タスクを消すのは `created_at + UPLOAD_LEASE_MS(10分) + CLEANUP_GRACE_MS(1時間)` を過ぎてから。それまでは cron のたびに同じキーを冪等に削除する。停止していたPUTが掃除の後に着地しても、次回の掃除で回収される(着地後の `isDeletionRequested` の読み取りに失敗しても、タスクは残っている)。
- `putImage` は R2 の `head` / `put` の待ちを `UPLOAD_LEASE_MS` で打ち切る(`503 upload_timeout`)。中断できない書き込みが後から着地し得ることは前提とし、上記の保持期間で覆う。
- (§12.3.6 で置き換え)保持期間は 1時間 → 7日 に延長し、前提に依存しない構成へ見直した。

#### 12.3.6 アップロードキーの一意化・状態管理・再走査(最終設計)

`withDeadline` は待機を打ち切るだけで R2 の PUT は中断できない。「待てば終わっているはず」には依存せず、次を組み合わせる。

1. **一意なR2キー**: `u/<userId>/<uploadId>`(sha256 ではない)。失敗・期限切れのキーは再利用されず、遅延PUTが既存の正常な画像を上書きしない。同内容の有効な画像が既にあれば、そのキーを共有して再送しない(`image_objects.r2_key` を参照。復活時は `r2_key` も更新)。`deleteImage` は同じ `r2_key` を指す行が無いときだけ本体を消す。
2. **状態管理**(`r2_cleanup_tasks.status`): `pending`(PUT完了未確認)→ 正常終了ならタスクごと削除 / 待機のタイムアウト・失敗なら `abandoned`。「PUTが完了した」(R2が成功を返した)ことと「D1へ登録した」ことは別で、完了を確認できたとき(`putSettled`)だけ削除依頼中の取り消しでタスクを消す。確認できないとき(タイムアウト)は、キーを一度削除してもタスクは消さない。
3. **PUT完了フック**: 待機を打ち切った後でPUTが終わったら、その場でキーを削除する(一意なキーなので誰も参照しない)。失敗しても 4,5 が回収する。
4. **掃除タスク**(`sweepCleanupTasks`): 削除依頼のあるユーザーのタスクは常に対象。生きているユーザーのタスクは、リース + 10分の余白を過ぎたものだけ(`image_objects` が参照していれば R2 に触れずタスクのみ捨て、参照が無ければキーを削除)。タスクは `CLEANUP_GRACE_MS`(7日)の保持期間が過ぎるまで消さず、cron のたびに冪等に削除する。
5. **プレフィックス再走査**(`sweepDeletions`): 削除完了後も、保持期間(リース + 7日)中は削除済みアカウントの `u/<userId>/` を cron のたびに再走査して削除する。タスクの記録が失われた書き込みも回収できる。
6. **完了の定義**: `completed_at` は「user 行の削除とR2プレフィックスの掃除が済み、有効なアップロードが無い」時点の記録。「以後R2に絶対残らない」という意味ではない。

**残存リスク(保証できない点)**: 中断できないPUTが保持期間(約7日)を超えて着地した場合は回収できない(アカウント単位の再走査は期間限定)。Cloudflare はサブリクエストの所要時間に上限を保証しておらず、タイムアウト後のPUTが着地しないことも保証されない。生きているアカウントの残骸キーも、保持期間後に着地すれば容量を消費するだけで残る(他者からは到達不能)。実環境での確認が必要。(再走査の打ち切りは §12.3.7 で廃止)

#### 12.3.7 同名の並行PUTと再走査の打ち切り廃止

- **不変条件**: R2の各キーは、(a) `image_objects` から参照されている、または (b) `r2_cleanup_tasks` で追跡されている、のどちらかを常に満たす。
- **並行PUT**: `image_objects` を上書きするバッチの先頭で、上書きで参照を失う旧キーを `abandoned` のタスクとして記録する(D1のbatchは原子的)。自分のタスクは成功後に消すが、旧キーのタスクは残る。生きているアカウントの掃除は、参照が無いキーだけを削除する(別名が同じキーを共有していれば触れない)。
- **再走査**: 削除済みアカウントのプレフィックス再走査(`sweepDeletions`)は打ち切らない。`account_deletions.last_scanned_at` で間隔を空ける(〜7日は毎回、〜90日は週1回、以降は月1回)。成功時だけ時刻を進めるので失敗は次回再試行される。1回の実行は50件まで。
- **限界**: 中断できないPUTの着地時刻の上限は保証できない。無期限の再走査で検出できるようにしたが、着地から次の走査まで(最大30日)はR2に残り得る。コストは削除済みアカウント数に比例する(長期的には棚卸しが必要)。
- `0003_account_deletions.sql` に `last_scanned_at` を追加(未マージのmigrationのため書き換え)。
